# SPEC: Simulation Core

Status: Approved (owner, 2026-10-20, after the NX-345 reference run) · Tracker: NX-100…NX-119 · ADRs: 0002, 0003

## 1. Purpose
This is the authoritative, deterministic world simulation. Everything else is input to it or a view of it.

## 2. Goals / Non-goals
- Goals: determinism, testability, a predictable tick budget, recovery from snapshots.
- Non-goals: rendering, networking, persistence I/O, and LLM calls (those live outside the kernel).

## 3. Requirements
- **SC-1** `step(state, commands, rng) -> (state, events)` MUST be deterministic and free of side effects outside `state`: no I/O, no wall clock, no global mutable state. For the tick budget (SC-10) `step` mutates the working state in place and returns it; it does not copy state per tick (Q-SIM-3). Callers must treat the state as owned by the kernel. In code this is `nexus.core.step.step(world, commands) -> events`: the RNG is `world.rng` (Q-SIM-32) and the world is the mutated state (NX-102).
- **SC-2** **Two clocks (Q-ALN-1).** The kernel steps at 10 Hz while running. Both clocks below are derived from the tick count, so both are deterministic, and both freeze while paused (SC-11).
  - **Game time** is the unscaled tick count: `TICK_DT = 0.1` game seconds per tick, so 1 game minute = 1 real minute while running. It drives player-facing durations: idle handoff and retire, ability cooldowns, the respawn delay (Q-ALN-5), and campaign and objective length. Per Q-ALN-23 it also drives the director decision window and tier dwell, the CP EMA window, the threat-memory and provocation half-lives, the Pattern of Life periods, the night-progress cap, the Tasking Board claim lease and priority aging, and the package fill wait.
  - **World time** is game time scaled by `sim.time_scale` (CONFIG-AND-CONTENT): `WORLD_DT = TICK_DT × sim.time_scale` world seconds per tick. It drives movement, logistics and combat, and per Q-ALN-23 also capture progress and decay, bridge repair, the FoW sensor (Tier 1 SIGINT) refresh and track fade. Rates for those in config are per world second and are multiplied by `WORLD_DT`.
- **SC-3** Given the same seed, config hash and command log, every replay MUST produce identical `state_hash` checkpoints on the same platform. Golden replays are pinned to the CI container image with exact Python and NumPy pins, and MUST match byte-for-byte there (Q-TEST-1).
- **SC-4** Entities have sequential integer ids. Every iteration over entities happens in id order.
- **SC-5** All randomness MUST come from `SimRng` sub-streams named per subsystem (`combat`, `director`, `spawn`, `objective`, `tasking`; the `fow` stream was removed by Q-FOW-5; never shared between subsystems, Q-SM-1). `tasking` is used only for the Tasking Board's seeded tie-break (Q-GD-37 item 5, Q-ALN-7). Each stream is PCG64 (NumPy's XSL-RR 128/64) whose state and increment come from blake2b, personalization `nexus.simrng.v1`, over the campaign seed and the stream name; changing that scheme changes every replay, so it needs a new personalization (Q-SIM-29).
- **SC-6** Commands MUST be applied in `(target_tick, arrival_seq)` order. The runtime stamps `target_tick = current_tick + 1` on admission (CONTRACTS §3), so a command is never late and there is no `late` flag (Q-SIM-1).
- **SC-7** Invalid commands MUST produce a `CommandRejected{reason}` event, never an exception.
- **SC-8** An exception inside `step` MUST NOT be survived in memory: `step` mutates in place (SC-1), so the half-updated state is discarded. The runtime logs a crash bundle and restores from the last snapshot plus the command log (Q-SIM-3). The crashed tick is replayed **with that tick's commands dropped**: the runtime appends a tombstone to the command log naming the tick, each dropped command is emitted as `CommandRejected{INTERNAL_ERROR}`, and replays honour the tombstone so they stay deterministic. Without this, a command that crashes `step` would crash every recovery (Q-SIM-2). A queued `JOIN` outlives its own tick in the reserve queue (world state), so on a tombstoned tick that is running the `lifecycle` system also drops the queue entries it would serve, one per free viewer slot and at least the head (the crashed tick may have freed the slot with one of its own, now dropped, commands), each as `CommandRejected{INTERNAL_ERROR}` with its own `arrival_seq`, in queue order; nothing is dropped from the queue while paused, since nothing is served then (NX-122). The commands must therefore be in the log before `step` runs (SYSTEM-DESIGN §5.2). A crash with no command cause (a bug in a system) raises again on the same tick; §6 bounds it: 3 crashes in 10 minutes pause the campaign and alert. Dropped commands get `event_seq` values like any other events, so replays reproduce them.
- **SC-9** Snapshots MUST round-trip losslessly: `hash(load(save(s))) == hash(s)`.
- **SC-10** Budgets: p99 `step` time < 25 ms at 1,000 entities and 500 viewer units (`slots.max_viewer_units`, Q-SIM-6) on the reference host (measured as `step` plus the frame build, Q-SIM-8): the owner's broadcast host, an i7-8700 with a GTX 1070 8 GB under WSL2 (Q-TEST-1). Re-baseline when the planned new PC replaces it. Spatial queries use uniform grids instead of O(n²) scans; sensing builds one per sensor range class, cell = the class's largest radius / 2 (§4 Sensing; NX-372, the Q-SIM-4 "optimize first, keep objects" decision). **Entity storage (Q-SIM-4):** entities are Python objects behind a small `World` API so systems never touch storage directly. A benchmark spike (1,000 entities, grid queries, one movement/sensor/combat pass, 500 viewer units) on the reference host decides before this spec is approved; objects stay unless the pass exceeds about 10 ms (Q-SIM-17: the spike also runs an idle case, 0 viewers and about 150 AI-only entities, to confirm the 24/7 idle load is small), in which case the hot fields move to NumPy arrays behind the same API.
- **SC-11** **A pause freezes the whole world (Q-CFG-8, Q-OPS-8, Q-OPS-9, Q-ALN-2):** every timer that changes sim state counts ticks, not wall-clock time: idle handoff/retire, despawn, respawn delay, ability cooldowns, logistics, capture, director windows and FoW timers. While `clock_paused` is set, for any reason (`PauseReasonCategory`, Q-ALN-3), neither game time nor world time advances: no unit moves, no combat resolves, no logistics or capture progresses, and no timer advances. Chat commands that do not change the world (`ME`, which `!status` aliases; a `JOIN` from a commander with no live unit, which always joins the reserve queue while paused, even when a slot is free, Q-ALN-26) still work; every other chat command that reaches the kernel is rejected with `CAMPAIGN_PAUSED` (CONTRACTS §5.2, STATE-MACHINES §4.4). **Staff, system and advisor commands while paused (Q-ALN-24, Q-ALN-36):** the safety actions always apply: `STAFF_BAN`, `FORGET` (including the despawn of the orphaned unit), `STAFF_KILL_SWITCH`, `STAFF_CAMPAIGN_PAUSE`, `STAFF_CAMPAIGN_RESUME` and `STAFF_CAMPAIGN_END`. `STAFF_CONFIG_RELOAD` is held and applied when the campaign resumes. `STAFF_DIRECTOR_OVERRIDE` is rejected with `CAMPAIGN_PAUSED`. `STAFF_UNBAN`, `STAFF_PURGE_UNITS` (including the despawn of the purged units) and `SYS_SET_CALLSIGN` apply; `ADVISOR_CHOICE` and the GM commands are rejected with `CAMPAIGN_PAUSED`, except `STAFF_GM_RELEASE`, which applies (Q-ALN-36). A pause and a resume enter only as logged commands (ADR-0002), so replays reproduce them.
- **SC-12** **Units and conversion (Q-CFG-8, Q-ALN-1, Q-ALN-6):** config durations use friendly units (s, min) and are converted to whole ticks once at config load, rounding **up** so a timer is never shorter than configured (Q-ALN-6): a game-time duration `d` seconds becomes `ceil(d / TICK_DT)` ticks; a world-time duration `d` world seconds becomes `ceil(d / WORLD_DT)` ticks. Each duration key's spec labels it game-time, world-time or real-time. Real-time timers (chat rate limits, digest batching, LLM/TTS budgets, reconnect backoff, the offline-pause trigger, and, per Q-ALN-4, taunt cooldowns, GM idle auto-release, redemption cooldowns and the supply-drop cap) live outside the kernel on a monotonic clock, are enforced before anything enters the sim, and reach the sim only as logged commands.
- **SC-13** **System order inside a tick (Q-SIM-7).** One constant list in code, asserted by a test: apply commands → director/AI orders → movement → sensing and fog (when due, FOW-5) → combat resolution (new shots fire, then pending impacts land) → logistics and capture → objectives → lifecycle (despawn, respawn, retire) → emit events, and `state_hash` when due. A write by one system is visible to later systems in the same tick, never earlier. A unit destroyed by combat this tick still moved this tick.
- **SC-14** **Event stream (Q-SIM-14).** `events` is the only way the rest of the system learns what happened; no consumer infers a change by diffing state, except the frame builder. Every event carries `tick`, a campaign-wide monotonically increasing `event_seq`, a type and ids only (no free text, no user strings). XP and merit ledger rows are built from events, and `<campaign_id>:<event_seq>:...` is their idempotency key (DATA-MODEL DM-4), so a recovery replay that re-emits an event cannot double-count.
- **SC-15** **Campaign end (Q-SIM-15).** When victory or defeat fires (GAMEPLAY §9) the kernel emits `CampaignEnded{outcome}` and from then on applies only the SC-11 safety actions. It never resets itself or starts the next war. The runtime builds a new kernel state for the next campaign (new seed, new config hash, units reset), so a replay never crosses a war boundary.
- **SC-16** **Replay scope (Q-SIM-13).** The seed, config hash and command log reproduce a campaign only on the same commit and pinned image. They serve golden CI replays, bug reproduction and crash recovery, not archives: a balance fix or a bug fix changes outcomes, so re-simulating an old log on new code is not promised. Public "watch the war again" replays come from output recorded at broadcast time, not from re-simulation.

## 4. World model (component-style, flat)
```
Entity { id:int, kind:UnitKind, side:Side(COALITION|ENEMY), domain:Domain(AIR|GROUND|SEA|STATIC),
         pos:Vec2(m), vel:Vec2(m/s), alt_band:(NOE|LOW|MED|HIGH) for AIR,
         hp:int, damage_state:DamageState(HEALTHY|DAMAGED|MISSION_KILL|DISABLED),
         fuel:fixed, munitions:{<weapon_id>:int}, gun_rounds:int, cargo:int,
         stance:Stance(PRESS|STANDARD|CAUTIOUS|GUNS),
         crew:{count:int, status:Crew(ABOARD|DOWNED|RESCUED|CAPTURED|LOST)},
         sensor:SensorProfile, weapons:[WeaponProfile], countermeasures:int, stealth:float,
         owner:OwnerRef(commander_id|AI_GARRISON|ENEMY_DIRECTOR), base_id?:NodeId (facilities only), follow_id?:EntityId (Q-GP-31, Q-GP-33), package_id?,
         order:Order(current), job_id?:TaskingJobId, path:[NodeId|Vec2], state:UnitState }
Node   { id:str(stable), name, kind:(AIRBASE|FOB|PORT|BRIDGE|HQ|SANCTUARY),
         pos, owner:Side|NEUTRAL, capture:CaptureState, stock:int, max_stock:int, hp:int }
Edge   { a:NodeId, b:NodeId, layer:(ROAD|SEA_LANE), length_m, speed_mult, bridge?:NodeId }
Campaign { id, seed, config_hash, mode, objective_mode:(TIMED|OFF), options:{unlimited_ammo:bool},
           start_tick, clock_paused, pause_reason:PauseReasonCategory?,
           pause_sub_reason:StaffPauseSubReason?, objective:Objective?, score }
```
- **In code now (`nexus.core.world`, NX-121, NX-122):** `Entity` has `id`, `kind`, `side`, `owner_kind`, `commander_id`, `callsign`, `pos`, `vel`, `hp`, `path`, `last_node`, `state`, `fuel`, `orbit`, and for aircraft `rearm_milli`, `rearm_spent` and `stalled` (refuel progress, NX-123 part 2, snapshot format 11), and for facilities `base_id`, `variant` (the theater's catalog variant, e.g. `SAM`) and `emitting` (FOW-11: `None` for a kind that never emits, `true` emitting, `false` dark; snapshot format 8, NX-150 part 2); the other fields above join with the system that first reads them. `state` holds the STATE-MACHINES §4.1 states in code so far, for aircraft only (NX-368): `LANDED`, `EN_ROUTE`, `ON_STATION`, `RTB` (kernel-internal until a frame or event carries it; `None` for other domains). `fuel` is an aircraft's world seconds of flight left (a float, hashed at the 1e-6 step, ADR-0002), and `orbit` the centre an idle `ON_STATION` aircraft circles (hashed in mm); both `None` otherwise (snapshot format 5). `hp` is `None` until the catalog has hp (combat, NX-124; Q-CFG-10). `World.respawn_left` maps a commander to the running ticks left of its respawn delay (GP-2), always ≥ 1; it is world state, in snapshots and `state_hash` (snapshot format 3). `World.reserve_queue` is the reserve queue (GP-3): the queued `JOIN` commands, head first, one per commander (U-4); it is world state too, encoded as each command's JSON data with sorted keys (snapshot format 4), and a snapshot that holds a commander twice is refused. `World.record_loss(commander_id)` sets it to `Rules.respawn_delay_ticks`; it is the hook the destroy and wreck paths call (NX-124), before `lifecycle` in their tick; `lose_unit` (the fuel crash, a unit lost at a captured base) calls it, and the shoot-down paths will. The `lifecycle` system counts every entry down by 1 per tick in commander-id order, not while paused (SC-11), and deletes it at 0, so a loss on tick L allows a JOIN on tick L + delay plus any paused ticks. `path` holds the remaining waypoints: node ids for GROUND, node ids or `Vec2` for AIR; a leading waypoint equal to `last_node` while the unit stands on that node counts as reached (a `shortest_path` route starts at its own node). `last_node` is the node a unit last reached or spawned at, so a GROUND unit is always on the road edge from `last_node` to `path[0]`. `World.stock` maps each finite-stock node to whole stock units (a SANCTUARY, the coalition's `haven` and the Static's rear source, is infinite by rule and absent); `start_campaign` fills it from the theater's `start_stock`. A cargo carrier (LOGI_TRUCK, ENEMY_CONVOY) has `cargo` (whole units aboard, else `None`), `unload_milli` (thousandths of a unit moved toward the next whole one, 0 to 999) and `delivered` (whole units unloaded in the current stop); all three are world state, in snapshots and `state_hash` (snapshot format 10, NX-123), and the loader refuses a format-9 snapshot. `World.owner` maps every theater node to its live owner (`COALITION`, `ENEMY` or `NEUTRAL`), starting from the theater's `start_owner`, and `World.capture` maps a node to its capture bar `CaptureBar{side, progress}` (progress in whole millionths of a percent, only while above 0); both are world state, in snapshots and `state_hash` (snapshot format 12, NX-125; the loader refuses format 11, and a bar with no owner entry for its node, with no progress or a full bar, or on its own side). `domain` is not stored: it comes from the unit catalog by `kind`. Static per-campaign data the kernel reads (`WORLD_DT`, `speed_mps` and `domain` by kind, the road graph, the role → kind map, the coalition sanctuary node, the logistics numbers (`Rules.supply`: each side's sanctuary, the nodes' starting owners, `logistics.node_max_stock` by node and its starvation floor, the cargo kinds, `logistics.truck_cargo`, `logistics.unload_rate` as thousandths per tick), `slots.max_live_per_commander`, `slots.respawn_delay_s` as game ticks rounded up, SC-12, `slots.max_viewer_units` and `slots.reserve_queue_max`, `min_speed_mps` and `fuel_s` per AIR kind, `air.bingo_reserve_frac`, `air.orbit_period_s`, `sensor.radius_m`, `stealth` and `sensor.passive_range_m` by kind (0 = none), `fow.paint_range_m`, the kinds that paint (RECON_UAV and ENEMY_RECON_UAV, named in `nexus.core.rules` until the catalog lists capabilities), `fow.sigint_range_mult`, `fow.sigint_refresh_s` as world ticks rounded up, `fow.sigint_cell_m` (which must divide the theater bounds) and `fow.sigint_size_m_min`/`_l_min`, the theater's masking regions rasterized to 1 km cells (Q-FOW-3), the AIRBASE and SANCTUARY node ids (`Rules.landing_nodes`: an aircraft lands at those its side owns now, `World.landing_bases(side)`, NX-125), every node's kind, the kinds whose catalog has weapons, the capture rules (`Rules.capture`, below) and the theater bounds; these keys are marked hot-reloadable but are not live yet: a config reload, when it exists, must rebuild `Rules` and log the change) is one frozen `nexus.core.rules.Rules`, held as `World.rules`; `make_rules` builds it from the loaded config. It is not world state, so it is in neither snapshots nor `state_hash` (`config_hash` covers it); `restore`/`recover` require it as `rules=` (`None` only for a world that never reads it) and re-attach it, refusing rules whose theater nodes differ from the snapshot's `World.owner` keys. `nexus.runtime.campaign_config.load_campaign_config` loads balance, the unit catalog and the theater from the shipped files (or given paths), and returns them with the `config_hash` and the `Rules`; the replay CLI uses it and refuses a snapshot whose campaign `config_hash` differs. `start_campaign(campaign_id, seed, config=None)` in the same module builds a new campaign's tick-0 world from it (the shipped files by default), stamped with its `config_hash` and with the `Rules` attached, and places the theater's `facilities` (NX-150 part 2): in theater-file order (so ids are deterministic), each is a `STATIC` entity at its base's position, on the base's starting side, `AI_GARRISON`-owned, `hp` null until combat (NX-124), with `base_id` and `variant`; RADAR_SITE and the SAM variant of AIR_DEFENSE_SITE start `emitting: true` (FOW-11, Q-FOW-10), every other facility `null`. Shipped-config golden cases start from it; `SimRuntime` refuses a world without rules, and a JOIN on such a world raises (SC-8 drops it). `CampaignStarted` lands with the campaign lifecycle (NX-126). `WORLD_DT` is computed once from `sim.tick_hz` and `sim.time_scale` in exact decimals (0.6 s at 6×).
- **Movement (SC-13 `movement` slot, NX-121):** in id order, each unit with a `path` spends `WORLD_DT` world seconds along it: AIR flies straight at `speed_mps`; GROUND drives road edges at `speed_mps × speed_mult` (GAMEPLAY §5). Time left after reaching a waypoint carries on to the next in the same tick; a reached waypoint is snapped to exactly. On reaching the last waypoint a ground unit stops (`vel` 0, `path` empty); an aircraft orbits or lands (below). `vel` is the heading to the next waypoint at the current speed, zero when idle. While `clock_paused`, nothing moves (SC-11). A path is followed as given; JOIN assigns one (below), routing around a destroyed bridge comes with NX-124 / NX-126.
- **Aircraft (same `movement` slot, NX-368, Q-SIM-38):** `speed_mps` is a top speed. `movement` picks the air rules by the kind's domain, and an AIR entity with no `state` is a bug (it raises); a snapshot whose entity has a `state` without `fuel` (or the reverse), or an `orbit` while not `ON_STATION`, is refused at load. A world with no rules moves nothing: only units with no path that are stateless or `LANDED` may be in it. Per tick, in id order: a `LANDED` aircraft with no path stays put (`vel` 0, no fuel burn). Otherwise, unless already `RTB`, the bingo check comes first: bingo when `fuel` ≤ the straight-line distance to the nearest landing base of its side ÷ `speed_mps` + `air.bingo_reserve_frac` × `fuel_s` (equality counts; ties by node id; a side with no landing base never bingos); at bingo its path becomes that base and its state `RTB`. A `LANDED` aircraft whose path is now just the landing base it stands on (a JOIN to its own sanctuary, or an order given at bingo) drops the path and stays landed without burning; any other path makes it take off (`EN_ROUTE`). Then it burns `WORLD_DT` of fuel (a constant burn per world second, a whole tick even on the takeoff and landing ticks) and moves or orbits (below). **Only after moving, fuel 0 is a crash** (owner, 2026-10-21): an aircraft that lands on the tick its fuel runs out stays landed (with fuel 0, which keeps it on the ground); any other is lost: after the loop, in id order, it is removed, `record_loss` starts its commander's respawn delay, and `UnitDestroyed{killer_id: null, assist_ids: [], side}` is emitted; the wreck and the crew-survival roll come with combat (NX-124). It flies its path at `speed_mps`. A path whose end is a landing base of its side (`RTB`, and any other path that ends there, as a later `!rtb` or move-to-base order will) lands it on arrival (`LANDED`, `vel` 0, `last_node` the base; it must end at the base node itself, so a `Vec2` waypoint after a base does not land); a path ending anywhere else puts it `ON_STATION`, orbiting a circle through the point it reached: entered along its last leg, turning clockwise on the map (so the centre of an eastbound arrival is one radius south), at `min_speed_mps`, one lap per `air.orbit_period_s` (PROPOSED 120 world s: radius = `min_speed_mps` × 120 / 2π, about 1.9 km for a jet and 380 m for a UAV). The orbit uses libm `atan2`, `cos` and `sin`, which are deterministic on one platform (ADR-0002); golden hashes are pinned to the CI platform. The circle's centre is clamped so the orbit stays in the theater bounds (a point within one radius of the edge snaps onto the clamped circle on the next tick; no strait-1 node is that close). A new path takes it off station (`EN_ROUTE`); `movement` keeps an `RTB` aircraft `RTB` whatever its path, so an order handler that gives an RTB aircraft a new path (NX-155, `!target`) must set it `EN_ROUTE` itself, which cancels the RTB. No airborne aircraft flies below `min_speed_mps`: it flies at `speed_mps` (≥ `min_speed_mps`, loader) or orbits at `min_speed_mps`; a clamp joins with the first slower speed (damage, NX-124; escort, NX-369). Bingo sits in `movement`, not `director`, because it is the unit's own fuel state, read and burned in the same slot; the Director's and Tasking Board's orders (NX-155) run before it. Paused: no burn, no orbit (SC-11). Refuel and rearm at a base are logistics (NX-123 part 2, `nexus.core.logistics`, below): a landed aircraft with no path at a landing base of its side buys fuel in the `logistics_capture` slot, and one ordered off with fuel at or below bingo stays on the ground (its order is dropped, as at its own base) and keeps refuelling; once it is above bingo a new order takes it off. An `RTB` aircraft whose path ends at a node that is no longer a landing base of its side (captured, NX-125) re-targets at once, in the same `movement` step, to the nearest landing base its side owns, by the bingo rule; with none left it flies on. Other RTB triggers (`!rtb`, munitions, mission-kill, idle retire) come with their items.
- **Logistics (SC-13 `logistics_capture` slot, `nexus.core.logistics`, NX-123; GAMEPLAY §5, GP-7, Q-GP-24, Q-SIM-48 to Q-SIM-54):** stock and cargo are whole integers and a unit leaves a source's stock as it becomes cargo, so their sum is conserved exactly; only a load at an infinite source adds, and a removed truck's cargo is lost. Stock also leaves for good as a spawn's loadout and as fuel: those debits are the `SupplyConsumed` events (open refuel stops included, `rearm_spent`), so stock + cargo + consumed is conserved. **Spawn:** a JOIN whose role maps to a cargo kind and whose target is a node *friendly* to the unit's side spawns the truck at its *source*, with `cargo` debited from that node at spawn. The source is the friendly node (never the destination) with a stock surplus, `stock - ceil(logistics.starve_threshold x node_max_stock)`, above 0, that has a road route to the destination, nearest by route metres (ties by node id); `cargo = min(logistics.truck_cargo, surplus)`, so a source never falls below its starvation floor. With no such node the side's SANCTUARY loads a full `truck_cargo`. Path: the road route source to destination. A neutral or enemy target, a node that holds no stock, or a null target or `hold` is a capture run or Holding: the truck spawns at the sanctuary with `cargo` 0 (the Tasking Board picks a job later, NX-155). Every other kind forward-deploys (JOIN, above) with `cargo` `None`. "Friendly" is the node's live owner (`World.owner`; capture changes it, NX-125). The Static has its own infinite rear source, `enemy_rear_source` (`static-rear`, Q-SIM-48), joined to its HQ by road and never capturable (N-4); a convoy of the Static (ENEMY_CONVOY, the same mechanic) is spawned directly by tests until the Director lands (NX-155). **Unload:** each running tick (not while paused, SC-11), in id order, a carrier with `cargo` > 0 standing at the end of its path moves `logistics.unload_rate x WORLD_DT` into its node: it adds the per-tick rate (whole thousandths) to `unload_milli`, moves the whole units, capped by its cargo and the node's room (`node_max_stock` minus `stock`), and keeps the fraction. At a full node, and when its cargo is 0, it stays parked, Holding (the retire is GP-5 / NX-324). A truck sent by its operator's command does not divert from a full base (Q-SIM-50, owner amendment 2026-10-21); the divert for AI and Tasking Board jobs lands with the board. **Lost destination:** a truck standing at a node no longer friendly to its side with cargo left drives to the nearest friendly base (a node with a stock maximum above 0, not a sanctuary) that has room, else to the nearest friendly base, else stays put, and unloads on arrival as above. **Event (lead decision, NX-123):** a stop at a node ends when the cargo reaches 0, the node reaches its maximum, or the truck drives off (lost destination); it then emits one `SupplyDelivered{node_id, amount, carrier_id, commander_id}` (CONTRACTS §6, `contracts/events/supply_delivered.json`) with `amount` = the units unloaded there during the stop, and none if that is 0. It is emitted for both sides; the public-view drop of ENEMY deliveries is downstream. `delivered` is reset when the event is emitted. A truck removed mid-stop emits nothing. `UnitSpawned` has no cargo field, only `loadout: FULL`. **Refuel (NX-123 part 2, Q-SIM-51, Q-SIM-53):** each running tick, in id order, after the trucks (no wall time, not while paused), an aircraft that is `LANDED` with no path at its `last_node` buys fuel when that node is one of its side's landing bases (AIRBASE or SANCTUARY, `World.landing_bases`; nowhere else, Q-SIM-42), and its kind's `loadout_cost` is above 0. Per tick it buys up to `logistics.rearm_rate x WORLD_DT` stock (whole thousandths, `Supply.rearm_milli`; the loader refuses less than 0.001 per tick), and one stock buys `fuel_s / loadout_cost` world seconds, so only the missing fuel is paid for: a full refill costs exactly `loadout_cost`. The last purchase is the exact remainder and sets `fuel` to the target (a conversion within 1e-6 thousandth counts as exact). A finite base is debited as the thousandths owed (`Entity.rearm_milli`, carried) reach whole units, never beyond its stock, so units debited = thousandths bought / 1000. Below its starvation floor (`stock` < `ceil(starve_threshold x max)`, checked each tick) the target is `logistics.starved_loadout.fuel_frac x fuel_s`, not `fuel_s`; at the sanctuary (infinite) the same rate runs with no debit and no cap. At 0 stock the aircraft gets nothing; the tick it first cannot buy it emits `RearmStalled{entity_id, node_id}` once (`Entity.stalled`; a resupply then a new stall emits again). A refuel stop ends when the aircraft is full or at the cap, stalls, or is no longer landed there (it takes off, or the node stops being friendly); it then emits one `SupplyConsumed{node_id, amount, cause: REARM}` with the whole units debited in the stop (`Entity.rearm_spent`), none for 0 (the node is `last_node` when the stop ends, which only differs if a takeoff reaches another node within one tick). Ground units have no fuel or ammo modeled, so they rearm nothing; guns and missiles wait for NX-124. Snapshot format 11 adds `rearm_milli`, `rearm_spent` and `stalled`; format 10 is refused.
- **Capture (SC-13 `logistics_capture` slot, after logistics; `nexus.core.capture`, NX-125; GAMEPLAY §8, STATE-MACHINES §4.2, Q-SIM-56, Q-SIM-57):** each running tick (not while paused, SC-11), for each node but a SANCTUARY or BRIDGE (never captured, N-4), in id order, from the units within `capture.radius_m` of it (a scan of every entity per node; no RNG). **Who counts:** GROUND units are capturers, a logistics unit weighing `capture.logi_weight`; airborne aircraft and facilities never count (N-3, Q-GP-38). A GROUND unit whose catalog has weapons is combat-capable. A defender that cannot contest (an unarmed ground unit, or an aircraft LANDED at the base) applies `capture.garrison_mult` (x3 on the capture time); an owner with no unit at the base applies `capture.empty_base_mult` (x0.5); a NEUTRAL node uses neither. **The bar:** per node, the side filling it and its progress as an integer of millionths of a percent (a full bar is 100,000,000), so thresholds and decay are exact. A side that is not the owner and has capturers is *free* when the other side has no combat-capable unit there. With no bar, one free side starts it (`CaptureStarted{node_id, side}`); with two free sides (a neutral node, both unarmed) the side with the larger capture weight (logistics units count `capture.logi_weight`) starts it and an exact tie starts nothing (Q-SIM-59); with none, nothing starts. A bar fills while its side is free and drains by `capture.decay_per_s` x `WORLD_DT` otherwise, abandoned or contested by a combat-capable unit (owner, 2026-10-21, Q-SIM-23); at 0 it is removed, the owner stays and the start rule applies again. A tick adds `max(1, round(100,000,000 x WORLD_DT / time))` with `time = max(capture.min_time_s, capture.time_s x quiet_mult(v) / n^capture.multi_unit_exponent x modifier)`, `n` the weighted capturers (1 per unit, `logi_weight` per logistics unit), `v` the live viewer units as JOIN counts them (`World.viewer_units`), and `quiet_mult` rising linearly from `capture.quiet_floor` at 0 to 1.0 at `capture.quiet_ref` for the coalition only (Q-SIM-26; the enemy's is 1.0); `n^exponent` uses libm `pow`, pinned to the CI platform like the orbit (ADR-0002). At 100% (N-1: one bar, one test per node per tick) the owner becomes the capturing side and the bar is removed, and in the same tick: `NodeCaptured{node_id, from, to, participant_commander_ids}` is emitted (participants: the commanders of the capturing side's units in radius, sorted, no duplicates); the facilities with that `base_id` switch side keeping their damage and everything else (Q-GP-25; the fog follow-ups are under Sensing); the previous owner's mobile units in radius, in id order, escape or are lost (Q-SM-10, Q-GD-32): a GROUND unit (a loaded truck included, its cargo stays aboard, and an open unloading stop ends with its `SupplyDelivered`) takes the road route to the nearest base its side owns (any owned node but a BRIDGE; ties by node id), from the node it is heading for if it is on the road, else from where it stands; an aircraft LANDED there whose fuel covers the straight line to the nearest landing base its side still owns, at top speed, takes off `RTB` to it; anything else is removed, `record_loss` starts a commander's respawn delay and `UnitDestroyed{killer_id: null, assist_ids: [], side}` is emitted, like the fuel crash. Airborne aircraft near the node are not at the base and are left alone. The crew-survival roll waits for combat (NX-124). A flip from NEUTRAL resolves no units (there is no losing side). The stock at the node stays with the node. Not in code yet: the base defense-HP gate (Q-GD-18, with combat), `CaptureProgress` (the spec gives no cadence), the idle floor on the `forward_airbase` (GAMEPLAY §9, needs the AUTO state), Disabled units, bridges, and objectives and momentum (NX-126).
- **Sensing (SC-13 `sensing` slot, `nexus.core.fog`, NX-150; FOG-OF-WAR Tier 1, Tier 2, FOW-11, FOW-13):** on ticks where `tick % fow.track_every_ticks == 0`, for each side, every enemy entity inside one of that side's sensors (`sensor.radius_m` × the target's `stealth`, inclusive; no RNG, Q-FOW-2) is tracked, found through uniform grids of the enemy entities, one per sensor range class (SC-10, NX-372): the positive `sensor.radius_m` values ascending, a class spans up to 4× its smallest radius and its cell is its largest radius / 2 (shipped catalog: 3–8 km in 4 km cells, 40–120 km in 60 km cells). Painters paint first, then every sensor tracks, longest first; a target leaves the grids once painted or tracked, which changes no result (both are unions) and cut the SC-10 smoke pass at 1,000 entities about in half. `World.contacts[side]` maps each known enemy id, in id order, to a `Contact{kind, pos, vel, age, painted}`: a tracked one holds the target's values at that pass with `age` null; when a pass no longer tracks it, those values freeze and `age` 0 starts a last-known track, which gains 1 per running tick and is dropped when it reaches `fow.track_fade_s` as world ticks (rounded up), whether or not the entity still exists (FOW-6a); tracking it again replaces it. A facility (STATIC domain) that stops being tracked is dropped instead: facilities never leave last-known tracks; a discovered marker (FOW-13, below) replaces them. `load` refuses a contact whose live entity is on the contact's own side or of another kind. `contacts` is world state (snapshot format 7, `state_hash` with positions in mm and velocities in mm/s). While paused nothing ages and no pass runs (FOW-9, SC-11). Readers use the last pass (Q-FOW-6): `tracked_by(world, side, id)`; `spotted(world, entity)` (FOW-12, derived from the enemy's contacts, not stored); `visible(world, side, entity)`, the FOW-1 predicate (own entities and current tracks; last-known tracks are not visible entities); and `side_view(world, side)`, a `SideView{side, tracks, last_known, nodes, owners, markers, blobs}` (`owners`: every node's live owner, FOW-10, NX-125) of copies that is the director's `EnemyView` for `ENEMY` (FOW-4, FOW-10). **Terrain masking (Q-FOW-3, part 2):** a GROUND target whose 1 km masking cell lies in one or more masking regions is tracked only by a sensor standing in one of those regions; STATIC targets are never masked; aircraft join when entities carry an altitude band (NOE/LOW by `default_alt_band`, NX-124). No strait-1 road crosses a masking region, so in the shipped theater masking takes effect only once aircraft have altitude bands; the FOG-OF-WAR §3 "LOW aircraft" test (Q-FOW-3) moves to NX-124, and `tests/core/test_fog.py` covers ground masking on a hand-made raster now. **Emitters and discovery (FOW-11, FOW-13, part 2):** a dark site (`emitting: false`) has no active or passive coverage. On each pass, a side observes an enemy facility it tracks, or an emitting one within `sensor.passive_range_m` of one of its non-dark passive sensors (no grid: emitters are the few pre-placed sites); observing writes `World.markers[side][id] = FacilityMarker{kind, variant, pos, emitting, confirmed_tick}` (the tick of that pass). A marker is never removed, not even when its entity is; an unobserved site's marker keeps its old values. `load` checks markers like contacts and refuses a `confirmed_tick` after the snapshot's tick. `side_view` carries a copy of the side's markers. **Painted (Q-FOW-6, part 2b):** on each pass a contact gets `painted: true` when a recon unit of the side (RECON_UAV, ENEMY_RECON_UAV) tracks it with its own sensor (its own `sensor.radius_m` × the target's `stealth`, masking included) within `fow.paint_range_m`; another sensor's track does not let it paint. A last-known track is never painted (`load` refuses one). It is stored on the contact, so snapshots and the hash carry it; combat reads it later (COMBAT track quality). The `TargetPainted{recon_id, target_id, until_tick}` event (CONTRACTS) arrives with combat (NX-124), `until_tick` being the next Tier 2 pass. **SIGINT (Tier 1, FOW-2, Q-FOW-5, Q-FOW-7, part 2b):** `World.sigint_age` counts running ticks (not while paused, FOW-9); when it reaches `fow.sigint_refresh_s` as world ticks (rounded up: PROPOSED 54 s is 90 ticks at 6×, 540 at 1×) it resets and each side's `World.blobs[side]` is rebuilt from scratch, after that tick's Tier 2 pass. The inputs are the enemy entities that are not STATIC, have a nonzero velocity on that tick, are not currently tracked by the side, and lie within `fow.sigint_range_mult` × `sensor.radius_m` of one of the side's own RADAR_SITEs that is not dark (FOW-11); masking and stealth do not apply. Q-FOW-7's "moving or emitting": emitting mobile units join when a mobile emitter exists (every emitter today is a facility, FOW-11). Each is counted in the square cell of `fow.sigint_cell_m` it lies in: `(cx, cy) = (floor(x / cell), floor(y / cell))`, each clamped into `[0, bounds / cell − 1]` (a unit on the east or north edge counts in the last column or row), index `cy × (w / cell) + cx`; `make_rules` refuses a `fow.sigint_cell_m` that does not divide both bounds, so every cell, and every blob centre, lies on the map. A `Blob{id, pos, size}` per non-empty cell, in index order: `id` `<refresh_tick>-<cell_index>`, `pos` the cell centre, `size` S below `fow.sigint_size_m_min` units, M below `fow.sigint_size_l_min`, L from there (PROPOSED 3 and 7: S 1–2, M 3–6, L 7+). No entity id, count or exact position, and no RNG draw. `side_view` carries the side's blobs; the director's `EnemyView` gets the same blobs from the enemy's radars (FOW-4). Blob building loops units × radar sites (radar sites are few pre-placed facilities): about 2 ms for one refresh at 1,000 entities in the SC-10 smoke test. Snapshot format 9 adds `painted`, `blobs` and `sigint_age`; `load` refuses a blob id that is not `<int>-<int>`, a side whose blobs mix refresh ticks, one after the snapshot's tick, cells out of order, or a `sigint_age` larger than the ticks since the blobs' refresh. **Base flips (NX-125, FOW-13):** when capture flips a base, each facility of it switches side (`fog.hand_over`): the new owner drops its contact and marker of the facility, since it is its own now, and the side that lost the base gets a marker with the site's values as of the flip tick, so it keeps knowing the site; a facility never leaves a last-known track.
- **SYS_SET_CALLSIGN (`nexus.core.handlers.set_callsign`, NX-370, Q-SIM-39):** stores `World.callsigns[commander_id]` (snapshot format 6; `load` checks the map), sets `callsign` on every live entity of that commander and emits `CallsignChanged{commander_id, callsign, callsign_kind}`; the schema checks the pattern. It applies while paused (Q-ALN-36; it changes no map state, SC-11). A JOIN, direct or served from the queue, copies the stored callsign onto the unit and `UnitSpawned.callsign` when it spawns (null if none). `COMMANDER_UNKNOWN` is not emitted: the kernel has no commander registry. `FORGET` will remove the entry.
- **JOIN (`nexus.core.handlers`, NX-122):** the kernel's handler table is `nexus.core.handlers.HANDLERS` (re-exported by `nexus.core.step`). A JOIN is checked in this order, each failure a `CommandRejected` (SC-7): paused and the commander has a live unit → `CAMPAIGN_PAUSED` (SC-11); `hold` with a target → `INVALID_PAYLOAD`; a role with no kind in `content/roles.yaml` (`NAVY`) → `ROLE_UNKNOWN`; the commander already has `slots.max_live_per_commander` live units → `UNIT_IN_SORTIE` (GP-1; retarget or role switch at base needs unit states); a `respawn_left` entry for the commander → `RESPAWN_COOLDOWN` (GP-2; growth with repeated losses and the crew-rescue reduction have no keys yet); any follow target → `FOLLOW_TARGET_INVALID` (until follow lands, Q-GP-31, Q-GP-33); an unknown node → `NODE_UNKNOWN`; a node target for a unit that is neither AIR nor GROUND, or a GROUND unit with no road route → `NODE_INVALID_FOR_UNIT`. A JOIN that passes every check queues (below) while paused (even with a free slot, Q-ALN-26), when the live `COMMANDER`-owned units reach `slots.max_viewer_units` (AUTO units are `COMMANDER`-owned, so they count, Q-ALN-9; the AUTO control flag itself is not in code yet), or while the queue is not empty (strict FIFO, U-4). Otherwise it spawns a `COALITION`, `COMMANDER`-owned unit of the role's kind at the sanctuary, or at its source for a cargo truck (below) (an aircraft `LANDED` with full `fuel_s`, taking off in `movement` when it has a path, NX-368) (forward deploy and its stock debit, below), with `callsign` taken from `world.callsigns` (set by `SYS_SET_CALLSIGN`, NX-370), `None` if the commander has none yet and emits `UnitSpawned{node_id: the spawn node, loadout: FULL}`. Path: none for a null target or `hold` (Holding); `[node]` for AIR; the `shortest_path` road route from the spawn node for GROUND. **Forward deploy (NX-123 part 2, GP-7, Q-SIM-54):** a non-carrier with a node target spawns, in `plan_deploy` (pure; the stock is debited in `_spawn`, so a queued JOIN is planned again when it is served), at the nearest candidate base to the target: a node in the theater's `spawns` list whose `domains` include the unit's domain, that the unit's side owns (`start_owner` for now, as above) and, for AIR, is also a landing base of the side (AIRBASE or SANCTUARY, Q-SIM-42: `spawns` AIR entries on an HQ or FOB are unused for now), and that holds at least `max(logistics.forward_deploy_min_surplus, loadout_cost)` stock above its starvation floor (GP-7 asks for both "exceeds the floor by the margin" and "never takes a base below its floor"; the larger of the two satisfies both). Nearest is the straight-line distance for AIR (path `[target]`) and the road-route metres for GROUND, which also needs a road route from the base to the target (ties by node id). The spawn has a FULL loadout (`fuel_s` for an aircraft, Q-SIM-53) and `logistics.loadout_cost.<kind>` leaves the base's stock at spawn with one `SupplyConsumed{node_id, amount, cause: SPAWN}` (CONTRACTS §6; none when 0); `UnitSpawned.node_id` is that base. With no candidate, a null target or `hold`, or a target that is the side's own sanctuary (it spawns there, free), the unit spawns at the sanctuary, which is never a candidate and is never debited. The function takes the side, so the Static's spawn (Director, NX-155) uses it unchanged. **Reserve queue (GP-3, STATE-MACHINES §4.1):** queueing appends the command to `World.reserve_queue` and emits `ReserveQueueJoined{commander_id, position}` (1-based); a commander already queued has its entry replaced in place by the new command (same position, event repeated); a newcomer to a full queue (`slots.reserve_queue_max`) is rejected with `RESERVE_QUEUE_FULL`. The `lifecycle` system, after the respawn countdown and not while paused, pops the head while live viewer units are below the cap and runs it through the same checks: a valid one spawns as above (its `UnitSpawned` is the "you're in"; it starts moving on the next tick, as `lifecycle` runs after `movement`), an invalid one (e.g. its route is gone) gets that check's `CommandRejected` with the queued command's `arrival_seq` and the next entry is served. Not in code yet: `ReserveQueueLeft`, milestone position updates (RQ-1), the `slots.queue_idle_min` timeout (runtime, real time), the dynamic cap (RQ-2) and removal on ban or forget.

- **Combat state (owner decisions 2026-10-17):**
  - `damage_state` follows Q-CBT-1 (Healthy → Damaged → Mission-kill → Disabled; Destroyed is the terminal lifecycle state, STATE-MACHINES §4.1) and is derived from the `hp` fraction (Q-GP-8, `combat.damage_state.*` thresholds). A hit does `damage × (1 − armor)` (COMBAT CB-5). Rolls use the `combat` stream. A Disabled unit is a wreck, removed after `combat.disabled_timeout_s` (COMBAT CB-7).
  - **Shots (Q-GP-7, Q-GP-12):** a shot is not an entity. Firing spends the round and stores a pending impact `Shot{id:int, shooter, target, weapon_id, impact_tick}` in state. Pending shots are part of the snapshot and the hash, get sequential ids, and land in `(impact_tick, id)` order. Pk is rolled on the impact tick against the target's state then; a target that is no longer tracked by the shooter's side, out of the envelope, destroyed or despawned makes the shot fizzle as a miss with no draw (Q-FOW-16). Guns land on the fire tick.
  - `munitions` holds the per-sortie load per weapon, drawn from base stock at spawn/rearm. **Guns are limited** (`gun_rounds`, high count) and rounds used are charged to base stock on resupply (Q-CBT-7). `unlimited_ammo` is a campaign option only, set at campaign setup by an Admin or the owner; a GM cannot change campaign options (Q-ALN-10).
  - `stance` drives auto-RTB: `STANDARD` at mission-kill, `CAUTIOUS` at Damaged, `PRESS` never, `GUNS` keeps fighting with guns after missiles/bombs run out (Q-CBT-6, Q-CBT-7).
  - `crew` is set from the platform's crew count; a seeded crew-survival roll on disable or shoot-down decides `DOWNED` vs `LOST`, and CSAR resolves `RESCUED` or `CAPTURED` (GAMEPLAY §6a).
  - Hit probability uses the first-build factors in COMBAT §5.2 (Q-CBT-10), capped at `combat.pk_cap`; unbuilt factors are a registered 1.0 (FB-6).
  - The Static's units carry the same fields and rules (parity, GAMEPLAY §0).
  - **Discovered facility markers (FOG-OF-WAR FOW-13):** per side, `FacilityMarker{entity_id, kind, variant, pos, ring_m, state|null, emitting|null, confirmed_tick}`; world state, in the snapshot and `state_hash`. In code (NX-150 part 2) the marker is keyed by `entity_id` and has no `ring_m` or `state` yet: they join with weapon ranges and hp (combat, NX-124).
  - **Facilities (Q-GP-21, Q-GP-25):** radars and air-defense sites (factories are parked) are ordinary `STATIC`-domain entities with a `base_id`. Their `side` follows the base's owner; when a base flips they switch side keeping their damage. New facility kinds are new catalog entries, not kernel code (CONFIG-AND-CONTENT §7a).
- **World scale (resolves critique #24):** the theater is about 400 × 240 km. Ground convoy speed is about 25 m/s (a 90 km road takes ~1 h of world time, about 10 real minutes at 6×), and strike aircraft fly about 250 m/s. The world-time multiplier `sim.time_scale` (default 6×, SC-2) shortens travel so a sortie lasts 3–8 real minutes. It scales only world time (movement, logistics, combat), never player-facing game-time durations (Q-ALN-1). Tune it with the balance harness.

## 5. Runtime (outside the kernel)
- **Threading (Q-SIM-9):** the sim runs on its own thread. Commands come in through a thread-safe queue and frames go out through another. GIL contention with the gateway and WebSocket loop is accepted for now. If the benchmark shows chat-ingest or WebSocket jitter, the sim moves to its own process or container; the queues are already the boundary, so that is mechanical.
- **Readers (Q-SIM-8):** because `step` mutates in place (SC-1), nothing reads the world while it runs. The overlay frame and, every 300 ticks, the snapshot serialization are built synchronously on the sim thread right after `step` and leave it only as finished immutable bytes. Their time counts inside the SC-10 budget. Compression and disk writes happen off-thread.
- A fixed-step accumulator on `time.monotonic()`. Catch up at most 3 steps, then record `tick_overrun` (SYSTEM-DESIGN §5.2).
- The inbox is a bounded queue with an admission cap. Overflow is rejected with a metric and reply aggregation.
- The command log is append-only JSONL plus zstd, flushed every 1 s, in one directory per campaign whose segments rotate by size and at snapshot boundaries (DATA-MODEL §6.2). Each tick's commands are appended before `step` (SC-8). For now the runtime flushes every tick (NX-103). SC-8 does not need that: on a `step` exception the runtime appends the tombstone and flushes before it restores, so the buffered commands are on disk in time. Per-tick flushing only shrinks what a process kill loses, so the 1 s cadence is a later optimisation.
- A snapshot is written when the runtime starts (the recovery base) and every 300 ticks. Retention keeps the newest 20 plus the earliest snapshot of each game hour. For now the snapshot is compressed and written on the sim thread (NX-103); moving that off-thread (Readers, above) comes later.
- **Restore** (`nexus.runtime.recovery`) loads the newest snapshot that verifies, falling back to older ones, and then replays every tick after it. The log names only ticks that had commands or a tombstone, so the caller gives the tick to stop at: after a `step` exception the runtime passes the tick before the crash. With no tick given, replay stops at the last tick the log names (never before the snapshot), so after a process kill a restart resumes there; empty ticks after it are not replayed. The log must continue the snapshot: a missing segment or a command on the wrong side of the snapshot's `last_arrival_seq` fails the restore. Both the live crash path and a restart go through `recover`. If a replayed tick raises and has no tombstone (the process died after the write-ahead flush but before the tombstone), `recover` tombstones that tick and retries, up to 3 attempts. A tick that raises although it is already tombstoned is a system bug: restore can't route around it, so it raises at once and needs a code fix.
- `state_hash` is computed every 100 ticks: blake2b over canonical msgpack of sorted, quantized state. Only the hash quantizes (1 mm, 1e-6; ADR-0002): snapshots store floats losslessly, so a restored run continues bit-identically. The RNG state is part of world state, so both the snapshot and the hash cover it.
- **Automatic pauses (outside the kernel):** when the broadcast has been offline longer than `ops.offline_pause_after_min` (real time, default 10, configurable), the runtime issues a pause with reason `TECHNICAL`; shorter blips and a single chat platform dropping do not pause (Q-OPS-8). On recovery the overlay shows "COMMS RESTORED" and a 30 s countdown, then the runtime issues the resume. The weekly maintenance window pauses with reason `MAINTENANCE` and the owner's Ceasefire mode with reason `CEASEFIRE` (Q-OPS-9, Q-ALN-3). Admins can override from the Command Center.
- **Recorded output (Q-SIM-18):** besides the command log, the runtime records a redacted coalition frame stream and a private full-truth frame stream per campaign. Public replays and clips use them (CLIPS-REPLAY §1); the truth stream is served only after the campaign ends. The P1 spike measures the storage.
- **Clean shutdown (Q-SIM-16):** a deliberate restart or deploy pauses the campaign (the weekly maintenance window already pauses with `MAINTENANCE`), forces a snapshot at the next tick boundary, flushes the command log and then stops, so a planned restart loses nothing. An unclean crash still recovers from snapshot plus log (SC-8).
- Timestamps the runtime writes (command log, snapshots, crash bundles) are UTC ISO-8601 (Q-CFG-8). None enters `state`.

## 6. Failure modes
| Failure | Behavior |
|---|---|
| Exception in step | Crash bundle `(seed, config, last snapshot, log tail, exception)` → tombstone the tick → restore to the tick before → rerun the tick with its commands dropped (SC-8) → continue. 3 crashes within 6,000 ticks (10 minutes of game time while running; counted in ticks, so replays and tests see the same window) → the runtime stops stepping and sets `halted`; the caller alerts and pauses the campaign with a logged pause command (SC-11, ADR-0002). If recovery itself fails, or a log flush or rotation fails, the runtime also halts and re-raises; the commands drained for that tick are lost from the inbox. A halted runtime is discarded and a restart goes through `recover`. The crash count lives per process, so bounding restart loops across processes is the supervisor's job |
| Tick overrun sustained | Shed load: lower viewer unit cap, coarser FoW update, alert |
| Snapshot write fails | Count it in `snapshot_failures` (the caller alerts), keep running, and retry at the next 300-tick interval |
