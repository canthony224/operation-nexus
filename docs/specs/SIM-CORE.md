# SPEC: Simulation Core

Status: Approved (owner, 2026-10-20, after the NX-345 reference run) · Tracker: NX-100…NX-119 · ADRs: 0002, 0003

## 1. Purpose
This is the authoritative, deterministic world simulation. Everything else is input to it or a view of it.

## 2. Goals / Non-goals
- Goals: determinism, testability, a predictable tick budget, recovery from snapshots.
- Non-goals: rendering, networking, persistence I/O, and LLM calls (those live outside the kernel).

## 3. Requirements
- **SC-1** `step(state, commands, rng) -> (state, events)` MUST be deterministic and free of side effects outside `state`: no I/O, no wall clock, no global mutable state. For the tick budget (SC-10) `step` mutates the working state in place and returns it; it does not copy state per tick (Q-SIM-3). Callers must treat the state as owned by the kernel. In code this is `nexus.core.step.step(world, commands) -> events`: the RNG is `world.rng` (Q-SIM-32) and the world is the mutated state (NX-102).
- **SC-2** **Two clocks (Q-ALN-1).** The kernel steps at 10 Hz while running. Both clocks below are derived from the tick count, so both are deterministic, and both freeze while paused (SC-11).
  - **Game time** is the unscaled tick count: `TICK_DT = 0.1` game seconds per tick, so 1 game minute = 1 real minute while running. It drives player-facing durations: idle handoff and retire, ability cooldowns, the respawn delay (Q-ALN-5), and campaign and objective length. Per Q-ALN-23 it also drives the director decision window and tier dwell, the CP EMA window, the threat-memory and provocation half-lives, the Pattern of Life periods, the night-progress cap, the Tasking Board claim lease and priority aging, and the package fill wait.
  - **World time** is game time scaled by `sim.time_scale` (CONFIG-AND-CONTENT): `WORLD_DT = TICK_DT × sim.time_scale` world seconds per tick. It drives movement, logistics and combat, and per Q-ALN-23 also capture progress and decay, bridge repair, the FoW sensor (Tier 1 SIGINT) refresh and track fade. Rates for those in config are per world second and are multiplied by `WORLD_DT`.
- **SC-3** Given the same seed, config hash and command log, every replay MUST produce identical `state_hash` checkpoints on the same platform. Golden replays are pinned to the CI container image with exact Python and NumPy pins, and MUST match byte-for-byte there (Q-TEST-1).
- **SC-4** Entities have sequential integer ids. Every iteration over entities happens in id order.
- **SC-5** All randomness MUST come from `SimRng` sub-streams named per subsystem (`combat`, `director`, `spawn`, `objective`, `tasking`; the `fow` stream was removed by Q-FOW-5; never shared between subsystems, Q-SM-1). `tasking` is used only for the Tasking Board's seeded tie-break (Q-GD-37 item 5, Q-ALN-7). Each stream is PCG64 (NumPy's XSL-RR 128/64) whose state and increment come from blake2b, personalization `nexus.simrng.v1`, over the campaign seed and the stream name; changing that scheme changes every replay, so it needs a new personalization (Q-SIM-29).
- **SC-6** Commands MUST be applied in `(target_tick, arrival_seq)` order. The runtime stamps `target_tick = current_tick + 1` on admission (CONTRACTS §3), so a command is never late and there is no `late` flag (Q-SIM-1).
- **SC-7** Invalid commands MUST produce a `CommandRejected{reason}` event, never an exception.
- **SC-8** An exception inside `step` MUST NOT be survived in memory: `step` mutates in place (SC-1), so the half-updated state is discarded. The runtime logs a crash bundle and restores from the last snapshot plus the command log (Q-SIM-3). The crashed tick is replayed **with that tick's commands dropped**: the runtime appends a tombstone to the command log naming the tick, each dropped command is emitted as `CommandRejected{INTERNAL_ERROR}`, and replays honour the tombstone so they stay deterministic. Without this, a command that crashes `step` would crash every recovery (Q-SIM-2). A queued `JOIN` outlives its own tick in the reserve queue (world state), so on a tombstoned tick that is running the `lifecycle` system also drops the queue entries it would serve, one per free viewer slot and at least the head (the crashed tick may have freed the slot with one of its own, now dropped, commands), each as `CommandRejected{INTERNAL_ERROR}` with its own `arrival_seq`, in queue order; nothing is dropped from the queue while paused, since nothing is served then (NX-122). The commands must therefore be in the log before `step` runs (SYSTEM-DESIGN §5.2). A crash with no command cause (a bug in a system) raises again on the same tick; §6 bounds it: 3 crashes in 10 minutes pause the campaign and alert. Dropped commands get `event_seq` values like any other events, so replays reproduce them.
- **SC-9** Snapshots MUST round-trip losslessly: `hash(load(save(s))) == hash(s)`.
- **SC-10** Budgets: p99 `step` time < 25 ms at 1,000 entities and 500 viewer units (`slots.max_viewer_units`, Q-SIM-6) on the reference host (measured as `step` plus the frame build, Q-SIM-8): the owner's broadcast host, an i7-8700 with a GTX 1070 8 GB under WSL2 (Q-TEST-1). Re-baseline when the planned new PC replaces it. Spatial queries use a uniform grid (cell = max sensor radius / 2) instead of O(n²) scans. **Entity storage (Q-SIM-4):** entities are Python objects behind a small `World` API so systems never touch storage directly. A benchmark spike (1,000 entities, grid queries, one movement/sensor/combat pass, 500 viewer units) on the reference host decides before this spec is approved; objects stay unless the pass exceeds about 10 ms (Q-SIM-17: the spike also runs an idle case, 0 viewers and about 150 AI-only entities, to confirm the 24/7 idle load is small), in which case the hot fields move to NumPy arrays behind the same API.
- **SC-11** **A pause freezes the whole world (Q-CFG-8, Q-OPS-8, Q-OPS-9, Q-ALN-2):** every timer that changes sim state counts ticks, not wall-clock time: idle handoff/retire, despawn, respawn delay, ability cooldowns, logistics, capture, director windows and FoW timers. While `clock_paused` is set, for any reason (`PauseReasonCategory`, Q-ALN-3), neither game time nor world time advances: no unit moves, no combat resolves, no logistics or capture progresses, and no timer advances. Chat commands that do not change the world (`ME`, which `!status` aliases; a `JOIN` from a commander with no live unit, which always joins the reserve queue while paused, even when a slot is free, Q-ALN-26) still work; every other chat command that reaches the kernel is rejected with `CAMPAIGN_PAUSED` (CONTRACTS §5.2, STATE-MACHINES §4.4). **Staff, system and advisor commands while paused (Q-ALN-24, Q-ALN-36):** the safety actions always apply: `STAFF_BAN`, `FORGET` (including the despawn of the orphaned unit), `STAFF_KILL_SWITCH`, `STAFF_CAMPAIGN_PAUSE`, `STAFF_CAMPAIGN_RESUME` and `STAFF_CAMPAIGN_END`. `STAFF_CONFIG_RELOAD` is held and applied when the campaign resumes. `STAFF_DIRECTOR_OVERRIDE` is rejected with `CAMPAIGN_PAUSED`. `STAFF_UNBAN`, `STAFF_PURGE_UNITS` (including the despawn of the purged units) and `SYS_SET_CALLSIGN` apply; `ADVISOR_CHOICE` and the GM commands are rejected with `CAMPAIGN_PAUSED`, except `STAFF_GM_RELEASE`, which applies (Q-ALN-36). A pause and a resume enter only as logged commands (ADR-0002), so replays reproduce them.
- **SC-12** **Units and conversion (Q-CFG-8, Q-ALN-1, Q-ALN-6):** config durations use friendly units (s, min) and are converted to whole ticks once at config load, rounding **up** so a timer is never shorter than configured (Q-ALN-6): a game-time duration `d` seconds becomes `ceil(d / TICK_DT)` ticks; a world-time duration `d` world seconds becomes `ceil(d / WORLD_DT)` ticks. Each duration key's spec labels it game-time, world-time or real-time. Real-time timers (chat rate limits, digest batching, LLM/TTS budgets, reconnect backoff, the offline-pause trigger, and, per Q-ALN-4, taunt cooldowns, GM idle auto-release, redemption cooldowns and the supply-drop cap) live outside the kernel on a monotonic clock, are enforced before anything enters the sim, and reach the sim only as logged commands.
- **SC-13** **System order inside a tick (Q-SIM-7).** One constant list in code, asserted by a test: apply commands → director/AI orders → movement → sensing and fog (when due, FOW-5) → combat resolution (new shots fire, then pending impacts land) → logistics and capture → objectives → lifecycle (despawn, respawn, retire) → emit events, and `state_hash` when due. A write by one system is visible to later systems in the same tick, never earlier. A unit destroyed by combat this tick still moved this tick.
- **SC-14** **Event stream (Q-SIM-14).** `events` is the only way the rest of the system learns what happened; no consumer infers a change by diffing state, except the frame builder. Every event carries `tick`, a campaign-wide monotonically increasing `event_seq`, a type and ids only (no free text, no user strings). XP and merit ledger rows are built from events, and `<campaign_id>:<event_seq>:...` is their idempotency key (DATA-MODEL DM-4), so a recovery replay that re-emits an event cannot double-count.
- **SC-15** **Campaign end (Q-SIM-15).** When victory or defeat fires (GAMEPLAY §9) the kernel emits `CampaignEnded{outcome}` and from then on applies only the SC-11 safety actions. It never resets itself or starts the next war. The runtime builds a new kernel state for the next campaign (new seed, new config hash, units reset), so a replay never crosses a war boundary.
- **SC-16** **Replay scope (Q-SIM-13).** The seed, config hash and command log reproduce a campaign only on the same commit and pinned image. They serve golden CI replays, bug reproduction and crash recovery, not archives: a balance fix or a bug fix changes outcomes, so re-simulating an old log on new code is not promised. Public "watch the war again" replays come from output recorded at broadcast time, not from re-simulation.

## 4. World model (component-style, flat)
```
Entity { id:int, kind:UnitKind, side:Side(COALITION|ENEMY), domain:Domain(AIR|GROUND|SEA|STATIC),
         pos:Vec2(m), vel:Vec2(m/s), alt_band:(NOE|LOW|MED|HIGH) for AIR,
         hp:int, damage_state:DamageState(HEALTHY|DAMAGED|MISSION_KILL|DISABLED),
         fuel:fixed, munitions:{<weapon_id>:int}, gun_rounds:int, cargo:int,
         stance:Stance(PRESS|STANDARD|CAUTIOUS|GUNS),
         crew:{count:int, status:Crew(ABOARD|DOWNED|RESCUED|CAPTURED|LOST)},
         sensor:SensorProfile, weapons:[WeaponProfile], countermeasures:int, stealth:float,
         owner:OwnerRef(commander_id|AI_GARRISON|ENEMY_DIRECTOR), base_id?:NodeId (facilities only), follow_id?:EntityId (Q-GP-31, Q-GP-33), package_id?,
         order:Order(current), job_id?:TaskingJobId, path:[NodeId|Vec2], state:UnitState }
Node   { id:str(stable), name, kind:(AIRBASE|FOB|PORT|BRIDGE|HQ|SANCTUARY),
         pos, owner:Side|NEUTRAL, capture:CaptureState, stock:int, max_stock:int, hp:int }
Edge   { a:NodeId, b:NodeId, layer:(ROAD|SEA_LANE), length_m, speed_mult, bridge?:NodeId }
Campaign { id, seed, config_hash, mode, objective_mode:(TIMED|OFF), options:{unlimited_ammo:bool},
           start_tick, clock_paused, pause_reason:PauseReasonCategory?,
           pause_sub_reason:StaffPauseSubReason?, objective:Objective?, score }
```
- **In code now (`nexus.core.world`, NX-121, NX-122):** `Entity` has `id`, `kind`, `side`, `owner_kind`, `commander_id`, `callsign`, `pos`, `vel`, `hp`, `path`, `last_node`, `state`, `fuel` and `orbit`; the other fields above join with the system that first reads them. `state` holds the STATE-MACHINES §4.1 states in code so far, for aircraft only (NX-368): `LANDED`, `EN_ROUTE`, `ON_STATION`, `RTB` (kernel-internal until a frame or event carries it; `None` for other domains). `fuel` is an aircraft's world seconds of flight left (a float, hashed at the 1e-6 step, ADR-0002), and `orbit` the centre an idle `ON_STATION` aircraft circles (hashed in mm); both `None` otherwise (snapshot format 5). `hp` is `None` until the catalog has hp (combat, NX-124; Q-CFG-10). `World.respawn_left` maps a commander to the running ticks left of its respawn delay (GP-2), always ≥ 1; it is world state, in snapshots and `state_hash` (snapshot format 3). `World.reserve_queue` is the reserve queue (GP-3): the queued `JOIN` commands, head first, one per commander (U-4); it is world state too, encoded as each command's JSON data with sorted keys (snapshot format 4), and a snapshot that holds a commander twice is refused. `World.record_loss(commander_id)` sets it to `Rules.respawn_delay_ticks`; it is the hook the destroy and wreck paths call (NX-124), before `lifecycle` in their tick, and nothing calls it yet. The `lifecycle` system counts every entry down by 1 per tick in commander-id order, not while paused (SC-11), and deletes it at 0, so a loss on tick L allows a JOIN on tick L + delay plus any paused ticks. `path` holds the remaining waypoints: node ids for GROUND, node ids or `Vec2` for AIR; a leading waypoint equal to `last_node` while the unit stands on that node counts as reached (a `shortest_path` route starts at its own node). `last_node` is the node a unit last reached or spawned at, so a GROUND unit is always on the road edge from `last_node` to `path[0]`. `domain` is not stored: it comes from the unit catalog by `kind`. Static per-campaign data the kernel reads (`WORLD_DT`, `speed_mps` and `domain` by kind, the road graph, the role → kind map, the coalition sanctuary node, `slots.max_live_per_commander`, `slots.respawn_delay_s` as game ticks rounded up, SC-12, `slots.max_viewer_units` and `slots.reserve_queue_max`, `min_speed_mps` and `fuel_s` per AIR kind, `air.bingo_reserve_frac`, `air.orbit_period_s`, each side's landing bases (its AIRBASE and SANCTUARY nodes by the theater's start owners, until capture makes ownership world state, NX-125) and the theater bounds; these keys are marked hot-reloadable but are not live yet: a config reload, when it exists, must rebuild `Rules` and log the change) is one frozen `nexus.core.rules.Rules`, held as `World.rules`; `make_rules` builds it from the loaded config. It is not world state, so it is in neither snapshots nor `state_hash` (`config_hash` covers it); `restore`/`recover` require it as `rules=` (`None` only for a world that never reads it) and re-attach it. `nexus.runtime.campaign_config.load_campaign_config` loads balance, the unit catalog and the theater from the shipped files (or given paths), and returns them with the `config_hash` and the `Rules`; the replay CLI uses it and refuses a snapshot whose campaign `config_hash` differs. `start_campaign(campaign_id, seed, config=None)` in the same module builds a new campaign's tick-0 world from it (the shipped files by default), stamped with its `config_hash` and with the `Rules` attached; `SimRuntime` refuses a world without rules, and a JOIN on such a world raises (SC-8 drops it). `CampaignStarted` lands with the campaign lifecycle (NX-126). `WORLD_DT` is computed once from `sim.tick_hz` and `sim.time_scale` in exact decimals (0.6 s at 6×).
- **Movement (SC-13 `movement` slot, NX-121):** in id order, each unit with a `path` spends `WORLD_DT` world seconds along it: AIR flies straight at `speed_mps`; GROUND drives road edges at `speed_mps × speed_mult` (GAMEPLAY §5). Time left after reaching a waypoint carries on to the next in the same tick; a reached waypoint is snapped to exactly. On reaching the last waypoint a ground unit stops (`vel` 0, `path` empty); an aircraft orbits or lands (below). `vel` is the heading to the next waypoint at the current speed, zero when idle. While `clock_paused`, nothing moves (SC-11). A path is followed as given; JOIN assigns one (below), routing around a destroyed bridge comes with NX-124 / NX-126.
- **Aircraft (same `movement` slot, NX-368, Q-SIM-38):** `speed_mps` is a top speed. `movement` picks the air rules by the kind's domain, and an AIR entity with no `state` is a bug (it raises); a snapshot whose entity has a `state` without `fuel` (or the reverse), or an `orbit` while not `ON_STATION`, is refused at load. A world with no rules moves nothing: only units with no path that are stateless or `LANDED` may be in it. Per tick, in id order: a `LANDED` aircraft with no path stays put (`vel` 0, no fuel burn). Otherwise, unless already `RTB`, the bingo check comes first: bingo when `fuel` ≤ the straight-line distance to the nearest landing base of its side ÷ `speed_mps` + `air.bingo_reserve_frac` × `fuel_s` (equality counts; ties by node id; a side with no landing base never bingos); at bingo its path becomes that base and its state `RTB`. A `LANDED` aircraft whose path is now just the landing base it stands on (a JOIN to its own sanctuary, or an order given at bingo) drops the path and stays landed without burning; any other path makes it take off (`EN_ROUTE`). Then it burns `WORLD_DT` of fuel (a constant burn per world second, a whole tick even on the takeoff and landing ticks) and moves or orbits (below). **Only after moving, fuel 0 is a crash** (owner, 2026-10-21): an aircraft that lands on the tick its fuel runs out stays landed (with fuel 0, which keeps it on the ground); any other is lost: after the loop, in id order, it is removed, `record_loss` starts its commander's respawn delay, and `UnitDestroyed{killer_id: null, assist_ids: [], side}` is emitted; the wreck and the crew-survival roll come with combat (NX-124). It flies its path at `speed_mps`. A path whose end is a landing base of its side (`RTB`, and any other path that ends there, as a later `!rtb` or move-to-base order will) lands it on arrival (`LANDED`, `vel` 0, `last_node` the base; it must end at the base node itself, so a `Vec2` waypoint after a base does not land); a path ending anywhere else puts it `ON_STATION`, orbiting a circle through the point it reached: entered along its last leg, turning clockwise on the map (so the centre of an eastbound arrival is one radius south), at `min_speed_mps`, one lap per `air.orbit_period_s` (PROPOSED 120 world s: radius = `min_speed_mps` × 120 / 2π, about 1.9 km for a jet and 380 m for a UAV). The orbit uses libm `atan2`, `cos` and `sin`, which are deterministic on one platform (ADR-0002); golden hashes are pinned to the CI platform. The circle's centre is clamped so the orbit stays in the theater bounds (a point within one radius of the edge snaps onto the clamped circle on the next tick; no strait-1 node is that close). A new path takes it off station (`EN_ROUTE`); `movement` keeps an `RTB` aircraft `RTB` whatever its path, so an order handler that gives an RTB aircraft a new path (NX-155, `!target`) must set it `EN_ROUTE` itself, which cancels the RTB. No airborne aircraft flies below `min_speed_mps`: it flies at `speed_mps` (≥ `min_speed_mps`, loader) or orbits at `min_speed_mps`; a clamp joins with the first slower speed (damage, NX-124; escort, NX-369). Bingo sits in `movement`, not `director`, because it is the unit's own fuel state, read and burned in the same slot; the Director's and Tasking Board's orders (NX-155) run before it. Paused: no burn, no orbit (SC-11). Refuel and rearm at a base are logistics (NX-123): a landed aircraft keeps the fuel it landed with, and one ordered off with fuel at or below bingo stays on the ground. Other RTB triggers (`!rtb`, munitions, mission-kill, idle retire) come with their items.
- **Sensing (SC-13 `sensing` slot, `nexus.core.fog`, NX-150 part 1; FOG-OF-WAR Tier 2):** on ticks where `tick % fow.track_every_ticks == 0`, for each side, every enemy entity inside one of that side's sensors (`sensor.radius_m` × the target's `stealth`, inclusive; no RNG, Q-FOW-2) is tracked, found through a uniform grid of the enemy entities (cell = max `sensor.radius_m` / 2, SC-10). `World.contacts[side]` maps each known enemy id, in id order, to a `Contact{kind, pos, vel, age}`: a tracked one holds the target's values at that pass with `age` null; when a pass no longer tracks it, those values freeze and `age` 0 starts a last-known track, which gains 1 per running tick and is dropped when it reaches `fow.track_fade_s` as world ticks (rounded up), whether or not the entity still exists (FOW-6a); tracking it again replaces it. A facility (STATIC domain) that stops being tracked is dropped instead: facilities never leave last-known tracks; their discovered markers (FOW-13) come in part 2. `load` refuses a contact whose live entity is on the contact's own side or of another kind. `contacts` is world state (snapshot format 7, `state_hash` with positions in mm and velocities in mm/s). While paused nothing ages and no pass runs (FOW-9, SC-11). Readers use the last pass (Q-FOW-6): `tracked_by(world, side, id)`; `spotted(world, entity)` (FOW-12, derived from the enemy's contacts, not stored); `visible(world, side, entity)`, the FOW-1 predicate (own entities and current tracks; last-known tracks are not visible entities); and `side_view(world, side)`, a `SideView{side, tracks, last_known, nodes}` of copies that is the director's `EnemyView` for `ENEMY` (FOW-4, FOW-10; node owners join when capture makes them world state, NX-125). Not in code yet (part 2): terrain masking, Tier 1 SIGINT, emitters, passive sensors and facility discovery, the painted flag.
- **SYS_SET_CALLSIGN (`nexus.core.handlers.set_callsign`, NX-370, Q-SIM-39):** stores `World.callsigns[commander_id]` (snapshot format 6; `load` checks the map), sets `callsign` on every live entity of that commander and emits `CallsignChanged{commander_id, callsign, callsign_kind}`; the schema checks the pattern. It applies while paused (Q-ALN-36; it changes no map state, SC-11). A JOIN, direct or served from the queue, copies the stored callsign onto the unit and `UnitSpawned.callsign` when it spawns (null if none). `COMMANDER_UNKNOWN` is not emitted: the kernel has no commander registry. `FORGET` will remove the entry.
- **JOIN (`nexus.core.handlers`, NX-122):** the kernel's handler table is `nexus.core.handlers.HANDLERS` (re-exported by `nexus.core.step`). A JOIN is checked in this order, each failure a `CommandRejected` (SC-7): paused and the commander has a live unit → `CAMPAIGN_PAUSED` (SC-11); `hold` with a target → `INVALID_PAYLOAD`; a role with no kind in `content/roles.yaml` (`NAVY`) → `ROLE_UNKNOWN`; the commander already has `slots.max_live_per_commander` live units → `UNIT_IN_SORTIE` (GP-1; retarget or role switch at base needs unit states); a `respawn_left` entry for the commander → `RESPAWN_COOLDOWN` (GP-2; growth with repeated losses and the crew-rescue reduction have no keys yet); any follow target → `FOLLOW_TARGET_INVALID` (until follow lands, Q-GP-31, Q-GP-33); an unknown node → `NODE_UNKNOWN`; a node target for a unit that is neither AIR nor GROUND, or a GROUND unit with no road route → `NODE_INVALID_FOR_UNIT`. A JOIN that passes every check queues (below) while paused (even with a free slot, Q-ALN-26), when the live `COMMANDER`-owned units reach `slots.max_viewer_units` (AUTO units are `COMMANDER`-owned, so they count, Q-ALN-9; the AUTO control flag itself is not in code yet), or while the queue is not empty (strict FIFO, U-4). Otherwise it spawns a `COALITION`, `COMMANDER`-owned unit of the role's kind at the sanctuary (an aircraft `LANDED` with full `fuel_s`, taking off in `movement` when it has a path, NX-368) (interim: forward deploy, GP-7, and stock debits join with logistics, NX-123), with `callsign` taken from `world.callsigns` (set by `SYS_SET_CALLSIGN`, NX-370), `None` if the commander has none yet and emits `UnitSpawned{node_id: sanctuary, loadout: FULL}`. Path: none for a null target or `hold` (Holding); `[node]` for AIR; the `shortest_path` road route from the sanctuary for GROUND. **Reserve queue (GP-3, STATE-MACHINES §4.1):** queueing appends the command to `World.reserve_queue` and emits `ReserveQueueJoined{commander_id, position}` (1-based); a commander already queued has its entry replaced in place by the new command (same position, event repeated); a newcomer to a full queue (`slots.reserve_queue_max`) is rejected with `RESERVE_QUEUE_FULL`. The `lifecycle` system, after the respawn countdown and not while paused, pops the head while live viewer units are below the cap and runs it through the same checks: a valid one spawns as above (its `UnitSpawned` is the "you're in"; it starts moving on the next tick, as `lifecycle` runs after `movement`), an invalid one (e.g. its route is gone) gets that check's `CommandRejected` with the queued command's `arrival_seq` and the next entry is served. Not in code yet: `ReserveQueueLeft`, milestone position updates (RQ-1), the `slots.queue_idle_min` timeout (runtime, real time), the dynamic cap (RQ-2) and removal on ban or forget.
- `pause_sub_reason` is set only when `pause_reason = STAFF` and is optional there (RAID, ABUSE, CONTENT, OTHER; Q-ALN-31, CONTRACTS §3.3).
- **Combat state (owner decisions 2026-10-17):**
  - `damage_state` follows Q-CBT-1 (Healthy → Damaged → Mission-kill → Disabled; Destroyed is the terminal lifecycle state, STATE-MACHINES §4.1) and is derived from the `hp` fraction (Q-GP-8, `combat.damage_state.*` thresholds). A hit does `damage × (1 − armor)` (COMBAT CB-5). Rolls use the `combat` stream. A Disabled unit is a wreck, removed after `combat.disabled_timeout_s` (COMBAT CB-7).
  - **Shots (Q-GP-7, Q-GP-12):** a shot is not an entity. Firing spends the round and stores a pending impact `Shot{id:int, shooter, target, weapon_id, impact_tick}` in state. Pending shots are part of the snapshot and the hash, get sequential ids, and land in `(impact_tick, id)` order. Pk is rolled on the impact tick against the target's state then; a target that is no longer tracked by the shooter's side, out of the envelope, destroyed or despawned makes the shot fizzle as a miss with no draw (Q-FOW-16). Guns land on the fire tick.
  - `munitions` holds the per-sortie load per weapon, drawn from base stock at spawn/rearm. **Guns are limited** (`gun_rounds`, high count) and rounds used are charged to base stock on resupply (Q-CBT-7). `unlimited_ammo` is a campaign option only, set at campaign setup by an Admin or the owner; a GM cannot change campaign options (Q-ALN-10).
  - `stance` drives auto-RTB: `STANDARD` at mission-kill, `CAUTIOUS` at Damaged, `PRESS` never, `GUNS` keeps fighting with guns after missiles/bombs run out (Q-CBT-6, Q-CBT-7).
  - `crew` is set from the platform's crew count; a seeded crew-survival roll on disable or shoot-down decides `DOWNED` vs `LOST`, and CSAR resolves `RESCUED` or `CAPTURED` (GAMEPLAY §6a).
  - Hit probability uses the first-build factors in COMBAT §5.2 (Q-CBT-10), capped at `combat.pk_cap`; unbuilt factors are a registered 1.0 (FB-6).
  - The Static's units carry the same fields and rules (parity, GAMEPLAY §0).
  - **Discovered facility markers (FOG-OF-WAR FOW-13):** per side, `FacilityMarker{entity_id, kind, variant, pos, ring_m, state|null, emitting|null, confirmed_tick}`; world state, in the snapshot and `state_hash`.
  - **Facilities (Q-GP-21, Q-GP-25):** radars and air-defense sites (factories are parked) are ordinary `STATIC`-domain entities with a `base_id`. Their `side` follows the base's owner; when a base flips they switch side keeping their damage. New facility kinds are new catalog entries, not kernel code (CONFIG-AND-CONTENT §7a).
- **World scale (resolves critique #24):** the theater is about 400 × 240 km. Ground convoy speed is about 25 m/s (a 90 km road takes ~1 h of world time, about 10 real minutes at 6×), and strike aircraft fly about 250 m/s. The world-time multiplier `sim.time_scale` (default 6×, SC-2) shortens travel so a sortie lasts 3–8 real minutes. It scales only world time (movement, logistics, combat), never player-facing game-time durations (Q-ALN-1). Tune it with the balance harness.

## 5. Runtime (outside the kernel)
- **Threading (Q-SIM-9):** the sim runs on its own thread. Commands come in through a thread-safe queue and frames go out through another. GIL contention with the gateway and WebSocket loop is accepted for now. If the benchmark shows chat-ingest or WebSocket jitter, the sim moves to its own process or container; the queues are already the boundary, so that is mechanical.
- **Readers (Q-SIM-8):** because `step` mutates in place (SC-1), nothing reads the world while it runs. The overlay frame and, every 300 ticks, the snapshot serialization are built synchronously on the sim thread right after `step` and leave it only as finished immutable bytes. Their time counts inside the SC-10 budget. Compression and disk writes happen off-thread.
- A fixed-step accumulator on `time.monotonic()`. Catch up at most 3 steps, then record `tick_overrun` (SYSTEM-DESIGN §5.2).
- The inbox is a bounded queue with an admission cap. Overflow is rejected with a metric and reply aggregation.
- The command log is append-only JSONL plus zstd, flushed every 1 s, in one directory per campaign whose segments rotate by size and at snapshot boundaries (DATA-MODEL §6.2). Each tick's commands are appended before `step` (SC-8). For now the runtime flushes every tick (NX-103). SC-8 does not need that: on a `step` exception the runtime appends the tombstone and flushes before it restores, so the buffered commands are on disk in time. Per-tick flushing only shrinks what a process kill loses, so the 1 s cadence is a later optimisation.
- A snapshot is written when the runtime starts (the recovery base) and every 300 ticks. Retention keeps the newest 20 plus the earliest snapshot of each game hour. For now the snapshot is compressed and written on the sim thread (NX-103); moving that off-thread (Readers, above) comes later.
- **Restore** (`nexus.runtime.recovery`) loads the newest snapshot that verifies, falling back to older ones, and then replays every tick after it. The log names only ticks that had commands or a tombstone, so the caller gives the tick to stop at: after a `step` exception the runtime passes the tick before the crash. With no tick given, replay stops at the last tick the log names (never before the snapshot), so after a process kill a restart resumes there; empty ticks after it are not replayed. The log must continue the snapshot: a missing segment or a command on the wrong side of the snapshot's `last_arrival_seq` fails the restore. Both the live crash path and a restart go through `recover`. If a replayed tick raises and has no tombstone (the process died after the write-ahead flush but before the tombstone), `recover` tombstones that tick and retries, up to 3 attempts. A tick that raises although it is already tombstoned is a system bug: restore can't route around it, so it raises at once and needs a code fix.
- `state_hash` is computed every 100 ticks: blake2b over canonical msgpack of sorted, quantized state. Only the hash quantizes (1 mm, 1e-6; ADR-0002): snapshots store floats losslessly, so a restored run continues bit-identically. The RNG state is part of world state, so both the snapshot and the hash cover it.
- **Automatic pauses (outside the kernel):** when the broadcast has been offline longer than `ops.offline_pause_after_min` (real time, default 10, configurable), the runtime issues a pause with reason `TECHNICAL`; shorter blips and a single chat platform dropping do not pause (Q-OPS-8). On recovery the overlay shows "COMMS RESTORED" and a 30 s countdown, then the runtime issues the resume. The weekly maintenance window pauses with reason `MAINTENANCE` and the owner's Ceasefire mode with reason `CEASEFIRE` (Q-OPS-9, Q-ALN-3). Admins can override from the Command Center.
- **Recorded output (Q-SIM-18):** besides the command log, the runtime records a redacted coalition frame stream and a private full-truth frame stream per campaign. Public replays and clips use them (CLIPS-REPLAY §1); the truth stream is served only after the campaign ends. The P1 spike measures the storage.
- **Clean shutdown (Q-SIM-16):** a deliberate restart or deploy pauses the campaign (the weekly maintenance window already pauses with `MAINTENANCE`), forces a snapshot at the next tick boundary, flushes the command log and then stops, so a planned restart loses nothing. An unclean crash still recovers from snapshot plus log (SC-8).
- Timestamps the runtime writes (command log, snapshots, crash bundles) are UTC ISO-8601 (Q-CFG-8). None enters `state`.

## 6. Failure modes
| Failure | Behavior |
|---|---|
| Exception in step | Crash bundle `(seed, config, last snapshot, log tail, exception)` → tombstone the tick → restore to the tick before → rerun the tick with its commands dropped (SC-8) → continue. 3 crashes within 6,000 ticks (10 minutes of game time while running; counted in ticks, so replays and tests see the same window) → the runtime stops stepping and sets `halted`; the caller alerts and pauses the campaign with a logged pause command (SC-11, ADR-0002). If recovery itself fails, or a log flush or rotation fails, the runtime also halts and re-raises; the commands drained for that tick are lost from the inbox. A halted runtime is discarded and a restart goes through `recover`. The crash count lives per process, so bounding restart loops across processes is the supervisor's job |
| Tick overrun sustained | Shed load: lower viewer unit cap, coarser FoW update, alert |
| Snapshot write fails | Count it in `snapshot_failures` (the caller alerts), keep running, and retry at the next 300-tick interval |
